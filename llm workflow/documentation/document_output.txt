SECTION 3: EDGE CASE ERRORS & WHY THEY OCCURRED
============================================================

3.1 Edge Case: None Input to add_todo()
------------------------------------------
User Input: "A" -> None
Error/Output: "Input must be provided"

Why This Occurred:
The check `if name == None or name == ''` explicitly handles None values.
This is correct behavior as None represents a missing/invalid input.


3.2 Edge Case: Whitespace-Only Input
------------------------------------------
User Input: "A" -> "   "
Error/Output: "TODO added to list"

Why This Occurred (BUG):
The current implementation does NOT validate whitespace-only strings.
The check `if name == None or name == ''` only catches empty strings, not
strings containing only spaces, tabs, or other whitespace characters.

Why It's a Problem:
- User enters "   " thinking they're providing input
- System accepts it as a valid todo name
- Results in cluttered todo list with meaningless entries

Recommended Fix:
Add stripping and validation:  
  if name is None or name == '' or name.strip() == '':
      return "Input must be provided"
  # Or strip the input and check:
  name = name.strip()
  if not name:
      return "Input must be provided"


3.3 Edge Case: Leading/Trailing Spaces in Numeric Input
------------------------------------------
User Input: "R" -> " 3"
Error/Output: (Works correctly)

Why This Occurred:
The int() function in Python automatically handles leading/trailing spaces:
  int(" 3") = 3

This is actually good behavior - no fix needed.


3.4 Edge Case: Zero as Index Input
------------------------------------------
User Input: "R" -> "0"
Error/Output: "number must be within list index range (1-5)"

Why This Occurred:
The isInRange() method checks `index >= 0`, but the user input "0"
gets converted to index -1 (because of the -1 adjustment).

This is CORRECT behavior because users are expected to input 1-based
indices, not 0-based. However, the error message could be clearer.

Recommended Improvement:
Add a more specific error message:
  if not self.isInRange(index):
      return f"number must be between 1 and {len(self._todo_list)}"


3.5 Edge Case: Special Characters in Todo Names
------------------------------------------
User Input: "A" -> "@#$%^&*()"
Error/Output: "TODO added to list"

Why This Occurred:
The implementation accepts any string input without character validation.

Is This a Problem?
- Technically not a bug, but could be confusing
- Special characters might display incorrectly in some terminal fonts
- Could cause issues if the todo list is saved to file later

Recommended Fix (Optional):
Validate for printable ASCII characters:
  if not all(c.isprintable() for c in name):
      return "Todo names can only contain printable characters"


3.6 Edge Case: Very Long Todo Names
------------------------------------------
User Input: "A" -> "A" * 10000
Error/Output: "TODO added to list"

Why This Occurred:
No input length validation is implemented.

Is This a Problem?
- Memory efficiency concern for very large apps
- Could cause display issues in terminal
- Good practice to set reasonable limits (e.g., max 200 characters)

Recommended Fix (Optional):
  MAX_TODO_LENGTH = 200
  if len(name) > MAX_TODO_LENGTH:
      return f"Todo name cannot exceed {MAX_TODO_LENGTH} characters"
  name = name[:MAX_TODO_LENGTH]  # Truncate if needed
